LLM · 01 · Tokenization and embedding

From text to vectors: tokenization and embedding

A network can only add and multiply numbers. Two small components turn a string into a matrix it can learn from: a tokenizer maps text to integer IDs, and an embedding maps every ID to a learned vector and stamps its position on it.

The story in one paragraph

A tokenizer cuts text into units from a fixed vocabulary and numbers them. A character tokenizer is a sorted list and two dictionaries. BPE grows the vocabulary by repeatedly merging the most frequent adjacent pair, so common fragments become single tokens. The IDs are names, not quantities, so the embedding treats each one as a one-hot vector and multiplies it by a table, which is the same as picking a row. Backward, the gradient is scattered back into the rows that were picked. Because the lookup is order-blind, a position vector is added to each row, either learned or computed from sines and cosines. The result is a (B, T, d) tensor: the input of attention.

01 · Why tokenize

A network only eats numbers, and text is not numbers

So we cut the text into units, give every unit an integer ID, and promise to learn one vector per ID. The only real decision is how big a unit is.

The trade-off: vocabulary size V against sequence length T

Characters: tiny V, long T. Words: huge V, short T, and every new word is an <UNK>. Subwords sit in between: a fixed V of a few ten thousand pieces, and any string can still be spelled with them.

Both numbers are paid for downstream

The embedding table holds V × d numbers (section 05). Attention does work proportional to T². The tokenizer decides both.

Subword pieces are illustrative; the exact split depends on the learned merges (section 03). GPT-2's vocabulary has 50,257 tokens, most of them whole common words with a leading space (shown as ·).

Explain

  • Step 1: characters. Every keyboard character is a token: the vocabulary is tiny and nothing is ever unknown, but the sentence is 22 tokens long and each token carries very little meaning on its own.
  • Step 2: words. Six tokens, each meaningful, but the vocabulary is open-ended: "cats" is a new word even though "cat" is known, and every typo, name and number is unknown.
  • Step 3: subwords. A fixed vocabulary of frequent pieces. Common words stay whole; rare words are spelled from pieces ("cat" + "s"). This is what every modern language model uses.
  • Step 4: the trade-off is V against T. Step 5: both are paid for later: V × d numbers in the embedding table, T² work in attention.

In your code

CharTokenizer is the first row; BPETokenizer is the third. There is no word-level tokenizer in the module, but BPE run to a large vocabulary behaves like one for common words.

02 · CharTokenizer

CharTokenizer: a sorted vocabulary and two dictionaries

encode(text) = [char_to_id.get(c, 0) for c in text]  ·  decode(ids) = ''.join(id_to_char.get(i, '<UNK>') for i in ids)  ·  decode(encode(x)) = x exactly when every character of x is in the vocabulary.
build_vocab(corpus)
  chars = sorted(set(all characters))
  vocab = ['<UNK>'] + chars          # id 0 reserved
  char_to_id = {c: i};  id_to_char = {i: c}

Encode is a dictionary lookup per character

"hello" → [2, 1, 3, 3, 4]. Sorting makes the IDs reproducible: the same corpus always gives the same table.

Decode is the inverse dictionary, joined

[2, 1, 3, 3, 4] → "hello". The round trip is exact: nothing was thrown away.

Anything outside the vocabulary collapses to id 0

"hi!" → [2, 0, 0] → "h<UNK><UNK>". The tokenizer is lossy exactly on the characters it never saw.

Vocabulary built from the corpus ["hello", "help"]: vocab_size = 6 including <UNK>. Same vocabulary and IDs are used by every example in this deck.

Explain

  • Step 1: build_vocab collects every character of the corpus into a set, sorts it, and puts <UNK> in front. Two dictionaries are built from the list: character → id and id → character. The id is simply the position in the sorted list.
  • Step 2: encoding walks the string and looks each character up. Positions matter: "hello" has two l's, so id 3 appears twice.
  • Step 3: decoding looks each id up in the reverse dictionary and joins. Because the mapping is a bijection on the vocabulary, the round trip is exact.
  • Step 4: .get(c, 0) is the only "intelligence": unknown characters become id 0. The information is gone; decode cannot bring it back.
  • Step 5: type anything. Characters outside {e, h, l, o, p} turn coral and map to 0.

In your code

src/core/tokenization.py: CharTokenizer.__init__ accepts a ready vocabulary; build_vocab derives one from a corpus; encode/decode are the two loops above. vocab_size counts the <UNK> slot.

03 · BPE · Training

BPE training: merge the most frequent pair, repeat

Corpus: hello, hello, help → hello × 2, help × 1. Each word is split into characters, the last one carrying the end-of-word marker </w>.

Start: every symbol is a token

vocab = ['<UNK>', 'e', 'h', 'l', 'o</w>', 'p</w>']. The marker is glued to the last character, so 'o</w>' is one symbol: "o at the end of a word" differs from "o inside a word".

Count adjacent pairs, weighted by word frequency

(h, e) occurs in hello (× 2) and help (× 1): 3. (e, l) is also 3; the tie goes to the pair counted first. Merge it everywhere, append 'he' to the vocabulary, record the rule.

Stop when the vocabulary is full, or no pairs remain

Five merges and each training word is one token. The vocabulary grew 6 → 11: merges only add tokens; the characters stay, so any string can still be spelled.

train() in src/core/tokenization.py: word_freq = Counter(corpus); loop { _count_byte_pairs → most_common(1) → _merge_pair → vocab.append }; stops at vocab_size (20 here) or when no pair is left.

Explain

  • Step 1: the start state. _get_word_tokens splits a word into characters and appends </w> to the last one, so the initial symbols are e, h, l, o</w>, p</w>. The frequency of each distinct word comes from Counter(corpus).
  • Steps 2–6: one merge each. _count_byte_pairs walks every word's token list and adds the word's frequency to each adjacent pair. The most frequent pair is merged by _merge_pair: a single left-to-right scan per word that replaces each adjacent occurrence by the concatenation. The new token is appended to the vocabulary and the pair is appended to merges.
  • Why frequency-weighted: a word that appears 1,000 times should count 1,000 times. Counting distinct words once would make rare and common words equal.
  • Ties: Counter.most_common(1) returns the first-inserted pair among equals, and pairs are inserted in word order, left to right. That is why (h, e) beats (e, l).
  • The loop ends when the vocabulary reaches vocab_size or no adjacent pair is left. Here the corpus runs out first: 11 < 20.

In your code

BPETokenizer.train is this loop; _build_mappings then numbers the vocabulary. Note three things that stop the class from running as written: it is declared with def instead of class, train calls _count_byte_pairs and _merge_pair without self., and __init__ spells id_to_token as it_to_token. The algorithm itself is right; the figures here run a line-for-line port of it.

03 · BPE · A richer corpus

A richer corpus: the merges find stems and suffixes

Corpus: low × 5, lower × 2, newest × 6, widest × 3. Drag the slider: one notch, one merge.

Two merges in, 'est</w>' is a token

A suffix shared by newest and widest. 'lo', 'ne', 'new' follow: stems. BPE discovers morphology from counts alone, with no notion of what a suffix is.

Unseen end-symbols become <UNK>

wide → wi | d | e</w>. No training word ends in 'e', so 'e</w>' is unknown and decodes to <UNK>. Byte-level BPE (GPT-2) starts from all 256 bytes, so nothing is ever unknown.

Same algorithm, vocab_size = 20: 11 symbols + <UNK> + 8 merges. Compression ratio = characters ÷ tokens over the corpus, as analyze_tokenization() reports it.

Explain

  • At 0 merges every word is spelled out; the corpus is 79 characters and 79 tokens. Each notch of the slider is one iteration of the training loop: the bars in the middle are the pair counts that decide the next merge, the coral bar is the winner.
  • Merge 1 is (e, s): 9 occurrences, from newest × 6 and widest × 3. Merge 2 glues it to t</w>: the suffix 'est</w>' now has its own id. Merges 3–6 build 'lo', 'ne', 'new', 'newest</w>'; 7 makes 'low</w>' whole; 8 starts on 'widest'.
  • After 8 merges the 79 characters are 28 tokens: a compression ratio of 2.8. The vocabulary is 20.
  • The text box encodes with the merges learned so far, word by word. "lowest" was never a training word, yet it becomes lo | w | est</w>: pieces of "low" and "newest".
  • "wide" shows the weakness of this implementation: 'e</w>' was never a symbol, so it is unknown. Production BPE starts from bytes, so the base vocabulary already covers everything.

In your code

03 · BPE · Encoding and decoding

Encoding replays the merges in the order they were learned

encode(text):
  for word in text.split():
    toks = list(word); toks[-1] += '</w>'
    for (a, b) in merges:           # learned order
      toks = merge_adjacent(toks, a, b)
    ids += [token_to_id.get(t, 0) for t in toks]

decode(ids):
  ''.join(id_to_token[i] for i in ids)
    .replace('</w>', ' ').split()   # then ' '.join

Order, not frequency

At encode time there are no counts, only the merge list. Replaying it in training order guarantees that a training word is cut exactly as it was when training ended.

Cost

Each merge rescans the word: O(|merges| × |word|), even when it cannot apply. Production tokenizers index merges by pair and cache whole words.

text.split() is the only pre-tokenization

"hello," keeps its comma, so it differs from "hello". GPT-2 pre-splits with a regex (words, numbers, punctuation, spaces) before merging.

Merges from the previous slide, all 8 applied. Vocabulary ids: lo = 14, w = 10, est</w> = 13.

Explain

  • Step 1: "lowest" is split like a training word: characters, with </w> glued to the last one.
  • Step 2: the merge list is replayed. Merge 1 (e, s) fires, merge 2 (es, t</w>) fires, merge 3 (l, o) fires. Merges 4–8 scan the word and find nothing: 'ne', 'new', 'newest', 'low</w>', 'wi' do not occur. Note that merge 7, (lo, w</w>), does not match lo | w | est</w>: this w is not at the end of the word.
  • Step 3: the surviving tokens are looked up in token_to_id; a token not in the table becomes 0.
  • Step 4: decode joins the token strings, turns every </w> into a space, and collapses whitespace. Word boundaries survive because exactly one token per word carries the marker.

In your code

_apply_merges is the replay loop; encode wraps it with text.split() and the id lookup; decode is the join-and-replace. create_tokenizer("bpe", vocab_size, corpus) builds and trains one in a single call.

  • What does encode("newest low") return, and what does decoding it give? [17, 18] → "newest low": both are whole tokens, and the two </w> markers become the space.

04 · From IDs to vectors · One-hot

An ID is a name, not a number: one-hot turns it into a vector

eid ∈ {0, 1}V has a single 1, at position id.   eidᵀ W = W[id]: multiplying a one-hot row by the (V × d) table selects row id of the table.

Why not feed the integer?

'l' = 3 and 'e' = 1 would make l three times e, and h = 2 "between" them. IDs carry no arithmetic meaning, so first make them all orthogonal: one one-hot vector per ID.

An embedding is a linear layer fed one-hots

The matmul does V × d multiplies, all but d of them by zero, and returns a copy of one row. Indexing returns the same row for free. That is all Embedding.forward does: weight.data[indices].

At scale the shortcut is not optional

V = 50,257, d = 768: the one-hot product would spend 38.6 million multiplies per token to copy 768 numbers.

W is the 6 × 4 table of section 05 (Xavier-uniform, numpy seed 7). id 2 is 'h' in the section-02 vocabulary.

Explain

  • Step 1: the integer 2 becomes e₂ = [0, 0, 1, 0, 0, 0]. Every ID is now a unit vector; all of them are orthogonal, none is "bigger" than another.
  • Step 2: a linear layer with a (V × d) weight. For a one-hot input the product is a sum over rows with weights 0, 0, 1, 0, 0, 0: row 2 comes out unchanged.
  • Step 3: so the layer is a lookup table. NumPy's W[2] gives the identical result with no arithmetic. The embedding is "just" the first linear layer of the network, with the matmul optimised away.
  • Step 4: at GPT-2 size the matmul would be absurd: V × d multiplies to copy d numbers.

In your code

Embedding.forward: embedded = self.weight.data[indices.data.astype(int)]. The comment there says "equivalent to one-hot multiplication but much more efficient"; this slide is that comment, in numbers.

Check yourself

  • What is e₃ᵀ W + e₃ᵀ W in terms of the table? 2 · W[3]: the same row, twice, which is what a batch containing 'l' twice produces.

04 · From IDs to vectors · Geometry

Why learned, dense vectors: similarity becomes geometry

One-hot: every token is equally far from every other

ei · ej = 0 for i ≠ j. The representation says nothing beyond identity, and it has V dimensions.

Dense: d numbers per token, free to move

Rows start random (middle: the 6 rows of W in their first two coordinates). Training nudges each row along its gradient; nothing stops two rows from ending up close.

Similarity is a dot product

cos(wi, wj) = wi·wj / (‖wi‖ ‖wj‖). At initialization the matrix is noise. What "similar" ends up meaning is decided by the loss: with next-token prediction, tokens used in the same contexts drift together.

Cosines computed from the same 6 × 4 table. Blue: similar direction, coral: opposite, pale: unrelated.

Explain

  • Step 1: the one-hot rows form the identity matrix. Their pairwise dot products are all 0: the geometry is as uninformative as it can be, and it costs V dimensions.
  • Step 2: the dense table has d dimensions per token and no constraint. Plotting two of the four coordinates shows six points scattered at random: that is what initialization gives you.
  • Step 3: with dense vectors, "how alike are two tokens" is a number: their cosine. Right now the numbers are noise (e.g. 'h' and 'o' happen to point the same way). Training changes them: the gradient (next section) pushes rows that help the loss in similar ways to similar places. The famous analogies (king − man + woman ≈ queen) are this geometry after training on a lot of text.

Check yourself

  • Which has more parameters per token: one-hot followed by a (V × d) linear layer, or an Embedding(V, d)? Exactly the same: V × d. They are the same layer.

05 · Embedding layer · Forward

Embedding(V, d): one table and one gather

input word
limit = sqrt(6 / (V + d))   # Xavier
W = uniform(−limit, limit, (V, d))

forward(ids):               # (B, T) ints
  assert 0 ≤ ids < V
  out = W[ids]              # (B, T, d)
  out._grad_fn = EmbeddingBackward(W, ids)

Init scale follows the table's shape

limit = √(6/(6+4)) = 0.775 here; √(6/(50,257+768)) = 0.0108 for GPT-2. Bigger tables start smaller.

Shape rule: the output appends d

(T,) → (T, d); (B, T) → (B, T, d). A repeated ID copies the same row again: 'l' at positions 2 and 3 of "hello".

W drawn with numpy default_rng(7) exactly as src/core/embeddings.py does; vocabulary from section 02: 0 <UNK>, 1 e, 2 h, 3 l, 4 o, 5 p.

Explain

  • Step 1: the whole layer is one matrix, V rows of d numbers. Xavier-uniform picks the range so that the variance of the outputs matches the inputs for a dense layer of that shape: limit = √(6/(fan_in + fan_out)) with fan_in = V and fan_out = d.
  • Step 2: the input is a list of IDs, i.e. positions in the vocabulary. The character chips show which row each ID names.
  • Step 3: the gather. Row 2, then row 1, then row 3 twice, then row 4, stacked in input order. The output has one more axis than the input, of size d. Try the buttons: "loop" gathers row 4 twice.
  • Step 4: parameters are V × d; memory is 4 bytes each. GPT-2's table alone is 147 MiB, about a third of the model.

In your code

Embedding.__init__ draws rng.uniform(-limit, limit, (vocab_size, embed_dim)); forward range-checks, gathers, wraps in a Tensor and attaches EmbeddingBackward when the weight requires a gradient. Note that the weight is created with the default requires_grad=False, so as written nothing is attached and parameters() returns a tensor the optimizer cannot update; the caller has to set weight.requires_grad = True.

Check yourself

  • Input shape (8, 128), d = 512: output shape and the number of float32 bytes it occupies? (8, 128, 512); 8 · 128 · 512 · 4 = 2,097,152 bytes = 2 MiB.

05 · Embedding layer · Backward

Backward: gather forward, scatter-add backward

E = onehot(ids) · W  ⇒  ∂L/∂W = onehot(ids)ᵀ · ∂L/∂E: row i of the weight gradient is the sum of the output gradients at every position t where ids[t] = i.
grad_W = zeros_like(W)          # (V, d)
np.add.at(grad_W, ids.flatten(),
          grad_E.reshape(-1, d))  # scatter-add
return (grad_W,)

Repeated IDs accumulate

'l' sits at positions 2 and 3, so row 3 receives both: [0.8, 0.9, 1.0, 1.1] + [1.2, 1.3, 1.4, 1.5]. np.add.at does this; grad_W[ids] += grad_E would keep only the last write.

Sparse by nature

Rows 0 and 5 were not in the batch: their gradient is exactly zero and they do not move this step. A token that never appears never learns.

Link to the optimizer deck

Rare tokens get rare, small gradients. With one global η (SGD) they crawl; Adam divides each row by its own gradient scale, so rare rows take relatively larger steps.

grad_E chosen as 0.0, 0.1, …, 1.9 so the sums can be checked by eye. In the code: EmbeddingBackward.apply in src/core/embeddings.py.

Explain

  • Step 1: the gradient arriving from above has the output's shape, (T, d): one row per position. Here T = 5 for "hello".
  • Step 2: each position's gradient row is sent to the table row that produced it. Position 0 came from row 2 ('h'), so row 2 gets grad_E[0]. This is the transpose of the gather.
  • Step 3: positions 2 and 3 both came from row 3 ('l'). Both rows of gradient land on the same table row and add up. Mathematically: onehot(ids)ᵀ has two 1s in row 3.
  • Step 4: rows that were never gathered get nothing. The gradient of the table is sparse: at most T nonzero rows per sequence, out of V.
  • Step 5: the optimizer deck's point about per-parameter scaling applies row by row here. A token seen once per million gets one gradient per million steps; Adam's second moment for that row is tiny, so its step is not.

In your code

EmbeddingBackward.apply: zeros, np.add.at, return. As written it reads self.indices.dots, which does not exist (it should be .data), so the backward raises until that typo is fixed.

Check yourself

  • A batch of 32 sequences of 128 tokens, V = 50,257: at most how many table rows get a nonzero gradient? 32 · 128 = 4,096, about 8% of the table, and fewer when tokens repeat.

06 · Position · The problem

The lookup is order-blind

Each row depends only on its own ID. Reverse the sentence and you get the same rows in a different order; anything that treats its input as a set, like attention, cannot tell the two apart.

Same three rows, permuted

A word-level vocabulary: dog = 7, bites = 3, man = 12. Both sentences gather rows 7, 3 and 12; only the order of the stack differs.

Attention is a weighted sum over rows

Permute the rows and its outputs permute with them, but nothing in the computation depends on which row came first. Summed or averaged, the two sentences are identical.

The fix: add a vector that depends only on t

xt = W[idt] + P[t]

Two ways to get P: learn it as a second table, or compute it from sines and cosines.

Toy rows with d = 4, chosen by hand. The ids are from an imagined word-level vocabulary, not the character vocabulary of section 02.

Explain

  • Steps 1–2: two sentences with the same words. The embedding gathers the same three rows for both; the only difference is which row sits in which slot.
  • Step 3: any operation that is symmetric in its inputs (a sum, a mean, and attention, which is a data-dependent weighted sum) gives the same answer for both. The information "who bit whom" has been lost before the model starts.
  • Step 4: the remedy is to make the row at slot t different from the same row at slot t′, by adding a vector that is a function of t alone. After this, "dog at position 0" and "dog at position 2" are different inputs.

In your code

EmbeddingLayer takes pos_encoding='learned' | 'sinusoidal' | None. With None the model is exactly this slide: order-blind.

Check yourself

  • Would a recurrent network have this problem? No: it reads tokens one after another, so order is built into the computation. Transformers read all at once, which is why they need explicit positions.

06 · Position · Learned

Learned positions: a second table, added row by row

X[b, t] = E[b, t] + P[t],  P ∈ ℝL × d trainable, L = max_seq_len. The same row P[t] is added in every sequence of the batch (broadcast over b).

Init: U(±√(2/d)) = ±0.707 at d = 4

About the same size as the token rows, on purpose: the two are added, so neither should drown the other.

Params: L × d, no structure between rows

GPT-2: 1,024 × 768 = 0.79M (3 MiB). Row t and row t + 1 share nothing; that neighbours are related must be learned from data.

Hard limit

A sequence longer than L has no row: forward raises. A position never seen in training keeps its random row.

Numbers: ids [2, 1, 3] ("hel") through EmbeddingLayer(vocab_size=6, embed_dim=4, max_seq_len=8, pos_encoding='learned'), numpy seed 7.

Explain

  • Step 1: E, the three gathered token rows for "hel".
  • Step 2: P is a second table with one row per position up to L = 8. Only the first T = 3 rows are used: position_embeddings[:seq_len]. They are reshaped to (1, T, d) so NumPy broadcasts the same rows across the batch.
  • Step 3: X = E + P[:3], element by element. Check the first entry: 0.460 + (−0.657) = −0.196.
  • Step 4: backward, addition passes the gradient through unchanged to E, and sums over the batch axis for P because that axis was broadcast. The slice puts the (T, d) gradient into rows 0…T−1 of an (L, d) zero array (section 07 draws this). And the limits of a table: no row beyond L, and rows rarely used in training stay close to random.

In your code

PositionalEncoding.__init__ draws rng.uniform(-limit, limit, (max_seq_len, embed_dim)) with limit = √(2/embed_dim); forward checks the input is 3-D, slices, adds. Like the token table, position_embeddings is created with requires_grad=False.

  • Batch of 16 sequences, all of length 10, L = 512: how many rows of P get a nonzero gradient, and how many terms are summed into each? 10 rows; 16 terms each.

06 · Position · Sinusoidal

Sinusoidal positions: a fixed table of clocks

PE[pos, 2i] = sin(pos · ωi),  PE[pos, 2i+1] = cos(pos · ωi),  ωi = 10000−2i/d.  For d = 4: ω = (1, 0.01).
position = arange(L)[:, None]      # (L, 1)
div_term = exp(arange(0, d, 2)
               · (−ln 10000 / d))  # ω, (d/2,)
pe[:, 0::2] = sin(position · div_term)
pe[:, 1::2] = cos(position · div_term)

Pair i is a clock turning ωi radians per position

Period 2π/ωi: 6.3 positions for the fastest pair, 628 for the slow pair here (ω = 0.01), about 47,000 for the slowest pair at d = 64. (sin, cos) is the hand's (y, x).

Like the digits of a number

Fast clocks separate neighbours, slow clocks give the coarse position. No two positions share a row, and no parameter was trained.

_compute_sinusoidal_table(max_len, embed_dim) in src/core/embeddings.py; create_sinusoidal_embeddings wraps the table in a Tensor. Broadcasting (L, 1) × (d/2,) gives (L, d/2).

Explain

  • Step 1: the table for d = 4. Row 0 is [0, 1, 0, 1]: sin 0 and cos 0. Row 1 is [sin 1, cos 1, sin 0.01, cos 0.01] = [0.841, 0.540, 0.010, 1.000]. Columns come in (sin, cos) pairs that share a frequency.
  • Step 2: a pair is a clock. Position advances the hand by ω radians; (sin, cos) are the hand's coordinates. The fast clock (ω = 1) completes a turn every 6.28 positions; the slow one (ω = 0.01) every 628. Drag pos and watch.
  • Step 3: the chart plots the four columns against position. The fast pair oscillates, the slow pair barely moves within 50 positions: it encodes the coarse location, the fast one the fine detail, like digits.
  • The code builds the whole table in four NumPy lines. div_term is ω: exp(−2i · ln(10000)/d) = 10000−2i/d. Multiplying a (L, 1) column by a (d/2,) row broadcasts to (L, d/2); sin fills the even columns, cos the odd ones.

In your code

_compute_sinusoidal_table also handles an odd embed_dim by dropping the last cosine column. EmbeddingLayer with pos_encoding='sinusoidal' stores the whole (max_seq_len, d) table as a Tensor and slices [:seq_len] at forward time.

  • For d = 8, what are the four frequencies? 100000, 10000−1/4, 10000−1/2, 10000−3/4 = 1, 0.1, 0.01, 0.001.

06 · Position · Sinusoidal, the whole table

The whole table, and why offsets are linear

Left columns oscillate fast, right columns slowly

d = 64, positions 0…127. By dim 62 the period is about 47,000 positions: within this window the column is nearly constant. Hover to read a value.

An offset is a rotation

[sin((p+k)ω), cos((p+k)ω)] = R(kω) · [sin(pω), cos(pω)]
R(θ) = [[cos θ, sin θ], [−sin θ, cos θ]]

The matrix depends on k only, not on p. So "the token k places back" is a fixed linear map of the current row, something a weight matrix can learn.

Dot products depend only on the distance

PE[p] · PE[p+k] = Σi cos(k ωi): the same for every p, and falling with |k|. Nearby positions look alike; far ones do not.

Check of the rotation with d = 4: pe[7] = (0.657, 0.754, 0.070, 0.998) and pe[10] = (−0.544, −0.839, 0.100, 0.995): the first pair turned by 3 rad, the second by 0.03 rad.

Explain

  • Step 1: the full table as a picture. Each row is one position's vector; each column is one dimension over positions. Pairs of columns share a frequency, so the stripes come in sin/cos pairs. Frequencies fall geometrically from 1 to 10000−62/64, so the right-hand columns hardly change over 128 positions.
  • Step 2: the property that makes this encoding more than a lookup. Shifting a position by k rotates every (sin, cos) pair by a fixed angle kωi, independent of where you started. A linear layer can therefore implement "look k tokens back" as one matrix, for all positions at once. This is the idea RoPE later applies inside attention.
  • Step 3: because the rotation is fixed, so is the dot product between two positions k apart: Σ cos(kωi). The chart (normalised by d/2) peaks at k = 0 and decays, with small ripples from the fast pairs. Attention, which scores pairs of tokens by dot products, gets a free "closeness" signal.

In your code

Nothing beyond the table: the rotation and dot-product properties are consequences of the sin/cos formula, not extra code.

Check yourself

  • Why can a learned table not offer the same guarantee? Nothing ties row t to row t + k; the relation would have to be learned separately for every (t, k).

07 · EmbeddingLayer · Forward

EmbeddingLayer: tokens → (B, T, d) in four moves

forward(tokens):            # (B, T) or (T,)
  if tokens.ndim == 1:      # add a batch axis
    tokens = tokens.reshape(1, -1)
  x = token_embedding(tokens)    # (B, T, d)
  if scale_embeddings: x = x * sqrt(d)
  if learned:    x = pos_encoding(x)  # + P[:T]
  if sinusoidal: x = x + PE[:T]
  return x[0] if squeezed else x

Why × √d

Xavier rows are tiny next to a sinusoid row, whose norm is √(d/2). V = 1000, d = 64: ‖e‖ ≈ 0.35 against ‖pe‖ = 5.66. Scaling by √64 = 8 lifts the token signal to 2.8 so position does not drown it. Off by default here.

parameters(): W, plus P only if learned

The sinusoidal table is data, not a parameter: never updated, never saved. GPT-2 small: 38.6M + 0.79M = 39.4M of its 124M parameters live in these two tables, about a third.

Numbers: tokens [[2, 1, 3]], d = 4, learned positions, seed 7: the same E, P and X as the learned-positions slide.

Explain

  • Step 1: the input is a batch of ID sequences. A single sequence (T,) is given a batch axis so the rest of the code sees (B, T) always.
  • Step 2: the token table is gathered: (B, T) → (B, T, d).
  • Step 3: optional scaling by √d. It matters when the position signal has a fixed, large scale (sinusoids) and the token table starts tiny. The original Transformer did this; GPT-2 does not.
  • Step 4: positions are added. Learned: PositionalEncoding.forward. Sinusoidal: the stored table is sliced to [:T], given a batch axis of 1 and added. None: nothing.
  • Step 5: the batch axis added in step 1 is removed again with output[0]. The result feeds attention.

In your code

EmbeddingLayer.forward is these lines; parameters() concatenates the token table with the position table when pos_encoding_type == 'learned'. Scaling uses Tensor multiplication so the graph records a MulBackward.

Check yourself

  • EmbeddingLayer(vocab_size=100, embed_dim=64, max_seq_len=512, pos_encoding='sinusoidal'): how many parameters? 6,400: the token table only.

07 · EmbeddingLayer · Backward

The backward pass, node by node

Backward rules are transposes: broadcast ↔ sum, slice ↔ zero-pad, gather ↔ scatter-add.

AddBackward: X = E + P[:T]

∂L/∂E = ∂L/∂X unchanged. ∂L/∂P[:T] = Σb ∂L/∂X: the batch axis was broadcast forward, so it is summed backward.

SliceBackward: P[:T] from P

Put the (T, d) gradient into rows 0…T−1 of a zero (L, d) array. Positions beyond T were not used, so they get nothing.

EmbeddingBackward: E = W[ids]

Scatter-add the (B·T, d) gradient into the rows named by ids. With scale_embeddings on, MulBackward multiplies by √d on the way down.

Then the optimizer

W −= η · ∂L/∂W and P −= η · ∂L/∂P, row by row. Only rows that were gathered or sliced have a nonzero gradient this step.

Shapes for the running example: B = 1, T = 3, d = 4, V = 6, L = 8. Grey rows are exactly zero.

Explain

  • Step 1: the loss gradient arrives at X with shape (B, T, d). The last forward op was an addition, so the gradient is copied to both inputs; for P the broadcast batch axis is summed away (_reduce_broadcast_grad in autograd.py).
  • Step 2: P[:T] was a slice of P. Its gradient is placed into a zero array of P's full shape: rows 3…7 stay zero.
  • Step 3: E was a gather from W. Its gradient is scattered back, adding where ids repeat. If the √d scaling was on, the gradient is multiplied by √d first.
  • Step 4: both tables are then updated by the optimizer, row by row, exactly like any other parameter. The sparsity of the gradients is what makes embedding training cheap: most of the table is untouched each step.

In your code

The three Function classes: AddBackward and SliceBackward in src/core/autograd.py, EmbeddingBackward in src/core/embeddings.py. Each returns one gradient per saved tensor; the autograd engine chains them from the loss back to W and P.

In practice (GPT-2)

Byte-level BPE, V = 50,257; d = 768; learned positions, L = 1,024; the output layer reuses W (logits = h · Wᵀ, "tied embeddings"). Newer models keep BPE but move position into attention (RoPE): the sinusoid's rotation idea, applied to queries and keys instead of added to the input.

Next

X has shape (B, T, d) and every row knows its token and its position. Attention takes it from here: it mixes rows by content, which is the next deck.

Check yourself, across the deck

  • Why does a character tokenizer never need <UNK> for text drawn from its training alphabet, and a word tokenizer always will? The alphabet is closed; the set of words is not.
  • In one sentence, what does BPE training optimise? Greedily, the number of tokens needed to write the training corpus, one merge at a time.
  • Why is an embedding lookup "the same" as a linear layer? A one-hot input times a (V × d) matrix is a row of the matrix; indexing just skips the zeros.
  • Why does the embedding gradient use scatter-add rather than assignment? Repeated ids must accumulate; assignment would keep one of them.
  • Learned versus sinusoidal positions in one line each? Learned: L × d free parameters, no structure, hard length limit. Sinusoidal: zero parameters, any length, offsets are rotations.
